# 1 作るものと優先順位

ブラウザを操作画面とし、本人1人だけが使うマインドマップWebアプリを作る。保存先はSQLiteに統一する。目標は、Xmindのように「考える速さを妨げず、枝を増やし、並べ替え、見やすく整う」使い心地である。中心トピックから自由に思考を広げ、キーボードでもマウスでも短い操作で編集できることを最優先する。

本書の指定は新アプリの実装仕様であり、Xmindの全機能や内部実装を再現するという意味ではない。Xmindで確認した操作は末尾の参照資料で示し、それ以外の数値・挙動は新アプリの設計判断とする。ブランド名、ロゴ、アイコン素材、独自テンプレート、ソースコードの複製はしない。スクリーンショットの配色や構造を参考に、独自のデザインシステムを作る。

優先順位は、データを失わないこと、日本語を自然に入力できること、枝の追加と移動が快適なこと、自動配置が崩れないこと、見た目の一貫性の順。共同編集・複数利用者・競合解決は対象外。AI生成、課金、公開サービス用ログインも初期版では作らない。

## 最初に採用する前提

- 主対象はMacのChrome。現行安定版と1つ前を試験対象にする。WindowsのChromeとEdgeも基本操作を確認する。

- 利用者は本人1人。Mac上のローカルサーバーとSQLiteファイルへ保存し、Chromeで開く。1マップ1編集画面を運用前提にし、共同編集・複数タブ間の競合検出やマージは実装しない。

- 日本語UI、日本語IME、ダークテーマを標準にし、ライトテーマとOS追従も用意する。

- 初期版はMac上でフロントとAPIを起動する。インターネットがなくてもローカルサーバーが動いていれば利用できる。サーバー停止中の独立したオフライン編集や端末間同期は対象外。

- スマホは閲覧・ズーム・簡易テキスト編集まで。デスクトップ同等の高度なドラッグや大量編集は後段とする。

- 中国系運営サービスへの依存を避ける。外部SaaSと主要ライブラリの運営元・ライセンス・保守状況を採用前に記録する。OSSの個々の貢献者の国籍は保証対象にしない。

# 2 完成したと判断する体験

ユーザーが新規マップを開き、中心に「Redis」と入力する。Tabで「レプリケーション」を追加し、Enterで同階層の「シャーディング」を追加する。子トピックを増やしても枝は重ならない。「障害対応」の枝へ項目をドラッグして付け替え、折り畳んで全体像を見る。ブラウザとサーバーを終了して再度起動してもSQLiteから内容が戻る。完成したマップ全体をPNG画像で保存できる。JSONでバックアップし、再読込して編集できる。

この一連の体験を、操作説明なしでもボタンを見つけられ、説明を読めばキーボードだけでも完了できる状態にする。

# 4 画面構成とデザイン

左上にマップ名と保存状態、上部に追加・Undo・Redo・検索・出力・ヘルプ。中央は広いキャンバス。右側に選択トピックの書式とメモを編集するサイドバーを配置し、閉じればキャンバスが広がる。右下にズーム値、拡大縮小、全体表示を置く。マップ一覧は別画面とし、編集領域を常時圧迫しない。

参考スクリーンショットの「暗い灰色の背景、色付き曲線、テキスト中心のトピック、青い選択枠、右と下の追加ボタン」を独自の寸法・アイコンで採用する。右の＋は子、下の＋は兄弟を追加する。左向き枝でもボタンの意味を逆転させず、子追加ボタンは外側に、兄弟追加は下側に表示する。

## UIの基準値

背景 #20252B、パネル #2B323A、本文 #F2F5F8、補助文字 #B6C0CB、選択色 #69B4FF。枝はピンク・青・緑・橙などから選び、色だけで状態を伝えない。本文16pxを基準、中心22px、ノード内余白は上下8px・左右12px、角丸10px。サイドバー幅は320px、上部バーは56pxを初期値とする。これらは独自仕様であり、Xmindの測定値ではない。

アイコンボタンは最低32pxのクリック領域、タッチ操作は44px以上。フォーカス輪郭と選択枠を区別する。選択枠の線幅を変えてもノードの実寸が変わらないように描画する。ノードが未選択のときは編集用の＋を常時並べず、選択またはキーボードフォーカス時に表示する。

## 必要な画面状態

新規作成、正常編集、選択なし、複数選択、テキスト入力、ドラッグ中、ファイル読み込み中、保存中、保存失敗、復旧候補あり、検索結果なし、オフライン、破損ファイル、対応外バージョンの画面を設計する。白紙やコンソールエラーだけで失敗を伝えない。

# 5 操作仕様

「選択状態」と「文字編集状態」を明確に分ける。ノードをクリックすると選択、ダブルクリック、SpaceまたはF2で文字編集。選択状態で通常の文字を入力すると末尾への追記でなく編集開始とし、既存テキストの選択範囲を全選択して置き換えられる。日本語IME開始時に文字を欠落させないこと。

以下は新アプリの標準キーバインド。参照製品の完全一致を前提にしない。ブラウザやOSと衝突する場合は操作ガイドに代替キーを示す。

| 操作 | キーボード | マウスと画面 |
| - | - | - |
| 子を追加 | Tab | 子追加＋または上部メニュー |
| 次の兄弟を追加 | Enter | 兄弟追加＋ |
| 前の兄弟を追加 | Shift+Enter | メニュー |
| 編集開始 | SpaceまたはF2 | ダブルクリック |
| 編集確定 | Enter | 外側クリック |
| 編集中の改行 | Shift+Enter | テキスト内 |
| 編集取消 | Escape | 編集開始時へ戻す |
| 選択の移動 | 矢印 | ノードクリック |
| 削除 | DeleteまたはBackspace | コンテキストメニュー |
| UndoとRedo | Cmd/Ctrl+Z、Cmd/Ctrl+Shift+Z | 上部ボタン |
| コピーと貼り付け | Cmd/Ctrl+C、Cmd/Ctrl+V | メニュー |
| 折り畳みと展開 | 初期版はボタンとメニュー | 子数付き開閉ボタン |
| 検索 | Cmd/Ctrl+F | 検索ボタン |
| 全体表示 | Cmd/Ctrl+Shift+F | 全体表示ボタン |
| JSONバックアップ | Cmd/Ctrl+S | 保存メニュー |
| パン | Spaceを押したままドラッグ | 背景ドラッグ、中ボタンドラッグ |

Spaceの編集開始とパンは競合させない。キー押下中にドラッグが成立した場合はパン、ドラッグせずキーを離した場合だけ選択ノードの編集を開始する。入力欄へフォーカスがある場合はSpaceを通常入力として扱い、キャンバス操作を発火しない。矩形選択はShiftを押したまま背景をドラッグ、複数選択の追加と解除はShift+クリック。背景の通常ドラッグはパンとし、モードを明確に分ける。

## 日本語入力と編集の確定

compositionstartからcompositionendまではEnter、Tab、Escapeを構造編集として扱わない。event.isComposingも検査する。変換確定のEnterで兄弟が増えてはならない。編集開始前の文字列を保持し、Escape取消とUndoで復元できる。テキスト範囲選択中のコピーは文字をコピーし、ノード選択中はサブツリーをコピーする。

空の中心ノードを許可せず、確定時に「中心トピック」へ戻す。新規の空ノードをEscapeで取消したときはノード自体を除去する。既存ノードの文字を空にした場合は「トピック」として確定し、意図せぬ枝の消失を避ける。2000文字を超えるノード本文は入力時に案内し、長文はメモへ誘導する。

## 追加と選択移動

Tabは選択ノードの最後の子を追加し、新ノードを編集状態にする。Enterは直後の兄弟を追加する。中心に対するEnterは主トピックを追加する。Shift+Enterは中心以外で直前の兄弟を追加。矢印は左右の実配置を尊重し、外向きは最初の子、内向きは親、上下は同階層の前後を基本にする。折り畳み中の隠れたノードへは移動しない。

## ドラッグと並べ替え

ドラッグの開始閾値はポインター移動5px。候補の親を枠で強調し、兄弟間への挿入は線で示す。ドロップ前に変更結果が分かるよう、元のノード位置は半透明で残す。親を自身または子孫へ変更する操作は拒否する。中心ノードの親変更は禁止。Escapeで取消。展開中の枝を移動すると配下すべてが移る。折り畳み枝も配下を保持して移る。

移動と並べ替えは一回のUndoで元へ戻す。キャンバス端での自動スクロールは境界40pxから開始し、速度を上限付きで増加させる。空白へドロップした場合は初期版では移動取消とし、勝手に独立トピックにしない。

## コピーと削除

ノードコピーは配下、メモ、書式を含み、貼り付け時はすべて新IDを割り当てる。複数選択で親子が重複した場合は最上位ノードだけを操作対象にする。標準クリップボードAPIを使える場合はアプリ専用JSONとプレーンテキストを扱い、不可ならアプリ内コピーを使って制約を案内する。

削除はサブツリー単位。20ノード以上を消す場合は件数付き確認を出す。その他は削除後にUndoできる通知を出す。中心は削除不可。削除後は親へ選択を移す。マップ自体の削除は一度ゴミ箱へ移し、30日復元可能にする。完全削除は明示確認が必要。

# 6 自動配置とキャンバス

マップを「親子関係のある木」と「表示座標」に分ける。座標は原則レイアウトエンジンが計算し、保存された親子関係や順序から再現する。初期版は右向きロジックチャートと、左右に枝を配るマインドマップの2構成。レイアウト切替でデータを変えない。

中心の直接の子にside=left/rightを持たせる。左右構成の新しい主枝は、その時点の左右の表示高さが小さい方へ割り当てる。以後はユーザーが変更しない限り側を固定するため、編集のたびに左右が入れ替わらない。子孫は主枝の側を継承する。

ノード幅はテキスト計測後に80〜320px、中心は最大360pxを初期値とする。長文は折り返し、改行を維持する。子サブツリーの必要高さを下から計算し、親を配下の中央に配置する。水平間隔48px、兄弟の最低縦間隔16pxを基準にする。関係線の装飾、選択枠、折り畳みボタンの領域を含めて衝突を検査する。

編集後は変更枝と祖先に必要な範囲だけ再計算し、無関係な主枝が大きく揺れないようにする。フォントの読み込み完了後に再計測する。丸め誤差で毎回座標が変わらない決定的なアルゴリズムにする。初期実装で木構造用の独自レイアウトを採用し、一般グラフエンジンが必要になったときだけ追加する。

枝は三次ベジェ曲線で描画し、主枝色を子孫へ継承する。線はノードより背面。折り畳みは子孫を描画対象から外し、隠れたノード数を表示する。表示だけを変え、データを削除しない。

パンは背景ドラッグ。ズームは10〜300%、ポインター位置を基準に拡縮する。トラックパッドの通常スクロールはパン、Ctrl/Meta付きホイールまたはピンチはズーム。キャンバス内で必要な場合だけデフォルト動作を抑止し、ブラウザ全体のズームやページ操作を無差別に奪わない。全体表示は全ノードの外接矩形と余白64pxを収める。選択ノードが画面外なら「選択へ移動」で中央へ戻せる。

# 7 データ設計

永続化するドキュメントと一時的なUI状態を分離する。選択・ホバー・現在のテキスト編集中状態・ドラッグ中座標はドキュメントに混ぜない。折り畳み、カメラ位置など閲覧状態は別のviewStateへ保存する。

以下のJSONは説明用にIDを短縮表記している。実装・保存時は documentId、rootId、nodes のキーと id／parentId／childIds の参照に有効なUUIDを用いる。

```json
{
  "format": "mindmap-document",
  "schemaVersion": 1,
  "documentId": "uuid",
  "title": "Redis",
  "revision": 12,
  "rootId": "n1",
  "layout": "mindmap",
  "nodes": {
    "n1": {"id":"n1","parentId":null,"childIds":["n2"],"text":"Redis","note":""},
    "n2": {"id":"n2","parentId":"n1","childIds":[],"text":"複製","note":"","side":"right","style":{"branchColor":"#F175A6"}}
  },
  "viewState": {"collapsedNodeIds":[],"camera":{"x":0,"y":0,"zoom":1}},
  "createdAt": "ISO8601",
  "updatedAt": "ISO8601"
}
```

親子は冗長なので、書き込み時に必ず整合性検査する。すべての非rootノードに親が1つだけあり、parentIdとchildIdsが一致し、循環・重複ID・到達不能ノードがないこと。childIdsの配列順序を正とし、別のindex値は持たない。任意文字列をIDにせずUUIDを使い、インポート時は長さ・文字種も検査する。

全変更をAddNode、EditText、MoveSubtree、DeleteSubtree、SetStyleなどのコマンドとして実行する。コマンドは入力検証→状態変更→Undo記録→保存要求を一単位にする。テキスト入力はセッション単位でUndoをまとめ、1文字ごとに履歴を増やさない。最低100操作、または50MBの小さい方をUndo履歴の上限とし、超過した古い履歴を落とす。Undoは再起動後には保持しないことをUIで説明する。

# 8 保存用データベースと復旧

**採用するDBはSQLite。マップ1件を、木構造を含むJSON文書として1行へ保存する。** 画面ではノードの辞書と親子IDで編集し、保存するときに文書全体を直列化する。RDBでもJSONを保存できるため、木構造だからグラフDBが必要ということではない。

SQLiteを選ぶ理由は、1人用で大規模な同時書き込みや分散運用が不要で、専用DBサーバーを管理せずにファイルとして永続化できるから。マップの読み書きは原則全体単位であり、ノード同士の複雑な横断検索は要求されていない。PostgreSQLやMongoDB、グラフDBを追加する運用負担に見合う利益は今はない。ブラウザ内IndexedDBだけを正式保存にするとブラウザデータ削除に依存するため採用しない。

## 保存テーブル

- maps: id TEXT PRIMARY KEY、title TEXT、document_json TEXT、schema_version INTEGER、updated_at TEXT、deleted_at TEXT NULL。document_jsonは有効なJSONであることをDBのCHECKとAPIのスキーマ検証で確認する。

- snapshots: id TEXT PRIMARY KEY、map_id TEXT、document_json TEXT、created_at TEXT。各マップの直近5世代を保持し、map_idには外部キーを設定する。

- schema_migrations: version INTEGER PRIMARY KEY、applied_at TEXT。DB構造の変更履歴を記録する。

ノードを別テーブルへ分解する必要はない。保存サイズの初期上限は1文書10MB。titleとupdated_atだけを一覧検索に使い、本文全文検索は後段。JSON内のrevisionは画面内の更新世代・古いレイアウト結果の破棄に使う番号であり、競合検出用ではない。共同編集、CRDT、OT、楽観ロック、BroadcastChannel、複数ユーザー用テーブルは作らない。

## 保存の流れと失敗時

編集から500msのdebounce、最長2秒で保存要求を出す。同じ編集画面からの保存要求は1本ずつ順に送る単純なキューとし、送信中の編集は次の最新版へまとめる。これは非同期通信で古い保存が後から届くことを避ける処理であり、複数ユーザーの競合制御ではない。

APIはJSONを検証し、SQLiteの1トランザクションで現在版と復旧スナップショットを更新する。コミット成功応答を受けて初めて「保存済み」と表示する。容量不足、通信断、サーバー停止は「未保存」とし、再試行とJSONダウンロードを案内する。beforeunloadだけに依存しない。未知の新しいschemaVersionは書き換えず、対応外として安全に開くのを拒否する。

## 配置とバックアップ

初期の保存先はユーザーが把握できる永続ディレクトリの data/mindmaps.sqlite。実行ファイル・一時ディレクトリ・コンテナの破棄される領域には置かない。Dockerで動かす場合は永続ボリュームを必須にする。アプリの再インストールでデータを消さない。

DB内スナップショットは誤編集からの復旧用で、ディスク故障対策のバックアップではない。SQLiteのバックアップAPIを使うバックアップコマンドを用意し、起動中のDBファイルを単純コピーしない。利用日の初回保存時に1日1回、別のbackupディレクトリへ整合したDBコピーを作り、直近7日分を保持する。加えてマップ単位のJSON出力を常時利用できる。別ディスクやユーザーが管理するバックアップ先への複製方法をREADMEに記載するが、外部サービスへ自動送信はしない。

復元はアプリ停止→現状DBを退避→バックアップを復元→整合性検査→再起動の手順とし、実際に1回リストア試験をする。「SQLiteだからバックアップ不要」と案内しない。

# 9 インポートと出力

ネイティブJSONは書式とメモを含む完全往復形式とする。ファイルサイズ上限10MB、最大10000ノード、最大深さ100を初期上限とし、超過時は元データを変えずエラーを示す。インポートは検証とプレビュー後に新規マップとして作り、既存マップを無言で置き換えない。

Markdownは見出しと箇条書きの階層から木を生成する。初期版では最初のH1を中心とし、以降の見出しは直前のより浅い見出しの子にする。見出しレベルが飛んだ場合も中間ノードは作らない。箇条書きは現在の見出しの子とし、ネストをそのまま階層へ写す。見出しがなければファイル名を中心にする。H1が複数ある場合は最初以外を中心直下に置く。通常の段落は直前ノードのメモへ追加し、コードブロックはメモのテキストとして保持する。空ファイルは拒否する。この規則をテストとヘルプに載せる。ノードのメモや書式など表現できない情報はエクスポート前に注意する。MarkdownからのHTMLは実行しない。

画像出力は初期版の必須機能。PNGを標準の出力ボタンにし、SVGも選べるようにする。SVGはすべてのノードと線を含む自己完結形式で、ノードはSVGのtext/tspanへ変換する。foreignObjectだけに依存した出力は禁止。PNGは書き出し時の倍率を1x/2xから選べる。巨大図は画像サイズを上限4096×4096pxとし、縮小または分割を案内する。画面に見える範囲だけを誤って出力しない。選択範囲出力は明示的なオプションにする。

PDFは次段階。初期版で提供する場合は画像PDFであることを明示し、検索可能な文字やベクター出力を保証しない。Xmindファイルは独自形式の互換性・ライセンス・バージョン差があるため初期版では未対応。単に拡張子を変えて互換をうたわない。

# 10 技術構成

推奨初期構成はTypeScript、React、Vite。キャンバスはDOMノードとSVG曲線を同じworld transform内に置き、文字入力とアクセシビリティを確保する。キャンバス全体をCanvasだけで描いて日本語編集や文字選択を後付けする構成は採らない。小さなNode.jsのAPIを同梱し、SQLiteドライバー経由で保存する。静的フロントとAPIは同一オリジンで配信する。状態管理ライブラリは小さく保ち、ドメインモデルをUIから分離する。

モジュールはdomain（型・不変条件・コマンド）、layout（寸法から座標を計算する純粋関数）、editor（選択・入力・ドラッグ）、storage（永続化・移行・復旧）、io（各形式）、ui（ツールバー・ダイアログ）、testsに分ける。DOM座標からworld座標への変換を一か所に集約し、ズーム中のドラッグで位置がずれる問題を避ける。

APIは GET /api/maps（一覧）、POST /api/maps（作成）、GET /api/maps/（読込）、PUT /api/maps/（保存）、DELETE /api/maps/（ゴミ箱へ）、POST /api/maps//restore（復元）を基本にする。SQLは必ずパラメーター化し、保存本文の上限と木構造をAPI側でも検証する。ブラウザからDBファイルへ直接アクセスしない。

React Flow等を採用する場合も木構造レイアウトやIME、Undoを自動で解決するものと考えない。最初に1000ノード試験を行い、必要な部分だけ採用する。サプライチェーンのため、lockfile、依存ライセンス一覧、主要依存のリポジトリ・更新日を残す。外部のAPIキーをフロントへ埋め込まない。

# 11 性能とアクセシビリティ

性能は初期版の受入目標であり、測定環境をREADMEへ残す。基準はApple Silicon Mac、8GB以上、Chrome安定版、1000ノード・深さ10・各ノード平均40文字。マップ表示2秒以内、追加・編集後の配置反映p95で100ms以内、ドラッグとパンのフレーム時間p95で33ms以内を目標とする。5000ノードはストレス試験とし、データ喪失やクラッシュを起こさず、遅延がある場合は処理中表示を出す。実測値を捏造しない。

大量ノードでは画面外の描画省略、折り畳み枝の非描画、計測キャッシュを使う。ただし選択や検索で必要なノードが描画されない状態を避ける。レイアウトが重い場合はWeb Workerへ移し、古いrevisionに対する結果を捨てる。

通常文字4.5:1のコントラスト、キーボード操作、見えるフォーカス、ARIAの名前を用意する。キャンバスと同期するアウトライン表示を提供し、スクリーンリーダーでも階層が追えるようにする。ボタンには「子トピックを追加」など意味のあるラベルをつける。reduce motionでは配置アニメーションを止める。標準アニメーションも120〜180msに収める。

# 12 セキュリティとプライバシー

ノード本文はテキストとして描画する。メモ内HTMLやSVGのスクリプトを実行しない。リンクはhttpとhttpsを原則に許可し、javascript等は禁止。外部リンクには別タブとnoopenerを使う。リンクプレビュー取得や画像の外部読み込みは初期版では自動実行しない。

編集内容は自分のローカルAPI以外の第三者へ送信しない。アクセス解析、広告SDK、AI APIは初期版に含めない。フォント・アイコン・スクリプトは可能な限り同梱し、外部CDN依存を避ける。初期サーバーは127.0.0.1にのみbindし、同一オリジン以外の更新リクエストを拒否する。DBとバックアップは静的公開ディレクトリの外へ置く。CSPを設定し、依存脆弱性検査をCIへ追加する。本人1人でもネット公開時の不正アクセス対策は別問題なので、インターネット公開は初期版の対象外。スマホからの利用を実装する際は公開範囲とアクセス制限を別途決める。自己ホストの起動・保存場所・バックアップ手順をREADMEへ明記する。

# 14 実装の順序とレビュー

段階1は仕様・画面骨格・データモデル・単純な木の描画。段階2は追加・編集・選択とIME、Undo。段階3はレイアウト・ドラッグ・折り畳み。段階4は保存と復旧、JSON往復。段階5は検索・書式・Markdown・画像出力。段階6は性能・アクセシビリティ・セキュリティ・全受入試験とする。

各段階で動く成果を残す。見た目だけ先に作り、保存やIMEを最後へ回さない。完成報告には起動コマンド、実装済みと未対応、試験結果、既知の問題、主要依存、バックアップ方法を含める。ユーザーが提供するリポジトリや環境がある場合は、その規約と既存コードを先に読む。

未決事項は、ローカル以外で使う場合の配置先とアクセス制限、スマホ編集の深さ、PDF出力の品質、Xmind互換、画像添付容量、画面上の製品名。初期版を止めないよう、本書のデフォルトで進め、外部費用・公開・認証・データ送信が発生する前にユーザーへ確認する。
